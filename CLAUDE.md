# Правила разработки

Эти правила обязательны для всех, кто пишет код в репозитории: для AI-агентов (Claude и других) и для людей. Пиши как senior-разработчик: код должен быть понятен человеку, который видит его впервые.

## 1. Проект

Collateral second opinion — независимая оценка квартиры в Тбилиси, которую заёмщик предлагает в залог: сопоставимые продажи с откалиброванным диапазоном, состояние по фото, сверка с отчётом лицензированного оценщика и проверка LTV по правилам NBG. Решение принимает кредитный специалист. Хакатон NBG AI & Open Banking 2026, трек AI in Finance, problem space AI1 Credit Risk & Lending. `docs/research/00_STRATEGY.md` описывает прежнее направление (Virtual Field Visit).

| Путь | Что это | Проверки |
|---|---|---|
| `collateral-engine/` | Оценка залога, состояние по фото, LTV, аудит, консоль специалиста (Python 3.12) | `make install` при первом запуске, затем `make check` |
| `server/` | Шлюз к TBC Open Banking (AIS), NestJS | `npm run lint && npm test && npm run test:e2e && npm run build` |
| `income-engine/` | Оценка дохода, правила NBG, аудит, консоль специалиста (Python 3.12) | `make all` при первом запуске, затем `PYTHONPATH=src python -m pytest -q` |
| `data/` | Синтетический датасет организаторов (100 клиентов) | — |
| `docs/research/` | Исследования и стратегия. Только локально, в git не попадает | — |

Новые сервисы создаются в корне по шаблону из §6 и §7 и добавляются в `docker-compose.yml`, CI и `README.md`.

## 2. Порядок работы

1. Прочитай код, который будешь менять, и соседние модули. Повторяй принятые в проекте подходы и не тащи новые библиотеки без необходимости.
2. Сделай минимальное изменение, которое полностью решает задачу. Не добавляй функций, абстракций и настроек «на будущее».
3. Пиши тесты вместе с кодом, в том же изменении (§9).
4. Перед завершением прогони проверки компонента из таблицы §1. Красная проверка — задача не закончена.
5. Если требование неоднозначно или решение необратимо, спроси, а не угадывай.
6. Существующий код с короткими именами (`a`, `s`, `cfg`) приводи к правилам только там, где его меняешь. Массовый рефакторинг — отдельной задачей.

## 3. Чистый код

- Функция делает одно дело, и это видно из её имени. Если для описания нужно «и», раздели её.
- Функция укладывается примерно в 30 строк, вложенность не больше 2–3 уровней. Используй ранний `return` вместо глубоких `if`.
- Никаких магических чисел и строк: лимиты, пороги, URL и версии живут в конфиге или в именованных константах.
- Нет мёртвого кода, закомментированных блоков, `print` или `console.log` для отладки, неиспользуемых импортов и переменных.
- Ошибки обрабатывай явно. Не глуши исключения (`except Exception: pass`, пустой `catch`). Лови конкретный тип и добавляй контекст.
- Чистые функции и неизменяемые данные — там, где это возможно. Побочные эффекты (сеть, диск, время, случайность) держи на краях и передавай через зависимости.
- Нет глобального изменяемого состояния. Зависимости передаются явно: через конструктор или DI.
- Читаемость важнее краткости. Не пиши «умные» однострочники, которые нужно расшифровывать.

## 4. Именование

- Весь код, идентификаторы, комментарии и коммиты — на английском. Тексты для пользователя — на грузинском и английском.
- Имя описывает смысл, а не тип: `declared_income_gel`, `consent_id`, `evidence_frames`, а не `data`, `tmp`, `obj`, `res`, `x2`.
- Единицы измерения и валюта — в имени, если они не очевидны из типа: `amount_gel`, `timeout_ms`, `yield_litres_per_cow`.
- Булевы переменные — вопросом: `is_verified`, `has_consent`, `should_retry`.
- Функции — глаголом: `fetch_transactions`, `estimate_income_range`, `buildConsentRequest`.
- Однобуквенные имена допустимы только для индексов в коротком цикле.
- Одно понятие — одно имя во всём проекте. Для данных Open Banking используй имена из спецификации API (§8).

## 5. Комментарии

- Код объясняет «что» сам: через имена и структуру. Комментарий объясняет только «почему»: неочевидное решение, обходной путь, ссылку на норму.
- Хороший комментарий: `# NBG Order 104/04 requires at least three randomly chosen liveness tasks`.
- Плохой комментарий пересказывает код: `# loop over accounts`, `// call the API`.
- Docstring или JSDoc пиши только для публичных функций, поведение которых не очевидно из имени и типов.
- Никаких TODO без номера задачи и никаких комментариев на русском.

## 6. Python

- Python 3.12. Аннотации типов у всех функций и публичных атрибутов. `from __future__ import annotations` не нужен.
- Данные на границах (API, конфиг, ответы LLM) описывай моделями pydantic v2, а не словарями без схемы.
- Деньги в логике лимитов, PTI и сумм кредита считай в `Decimal`. В ML-признаках допустим `float`.
- Пути строятся через `pathlib.Path` от корня пакета, без строковой склейки.
- Логи — модуль `logging`, а не `print`.
- Структура нового сервиса:
  ```
  <service>/
    pyproject.toml        # зависимости с точными версиями (==), ruff и pytest
    src/<package>/
    tests/
    README.md
  ```
- В новых сервисах форматирование и линтер — `ruff format` и `ruff check`, тесты — `pytest`.

## 7. TypeScript и NestJS (`server/`)

- `strict` TypeScript, без `any`. Для внешних данных используй `unknown` и проверяй их.
- Один NestJS-модуль на раздел API, повторяя структуру TBC API reference:
  ```
  server/src/
    main.ts, app.module.ts
    config/              # чтение и проверка переменных окружения
    common/              # фильтр ошибок problem+json, X-Request-ID
    tbc-client/          # HTTP-клиент к песочнице: базовый URL, заголовки, таймауты, повторы
    oauth/               # authorization code + PKCE, обновление токена
    ais/
      consents/          # /v1/consents
      accounts/          # /v1/accounts, /v1/accounts/{account-id}
      balances/          # /v1/accounts/{account-id}/balances
      transactions/      # /v1/accounts/{account-id}/transactions
  ```
- В модуле лежат `<name>.module.ts`, `<name>.controller.ts`, `<name>.service.ts`, `dto/`, а тесты `*.spec.ts` — рядом с кодом. Имена файлов в kebab-case.
- Контроллер только принимает запрос и отдаёт ответ. Логика живёт в сервисе, HTTP к песочнице — только в `tbc-client`.
- Конфигурацию бери из переменных окружения через `config/`, например `TBC_API_BASE_URL`. Значения в коде не зашиваются.
- Форматирование — `npm run format` (prettier), линтер — `npm run lint` (oxlint).

## 8. Формат Грузинского Open Banking API

Грузинский стандарт основан на Berlin Group NextGenPSD2. Источник истины для путей, полей и заголовков — спецификация песочницы: https://tbc-bank-mock-open-banking-api.vercel.app/openapi.json

- Пути, имена полей и заголовков бери ровно как в спецификации: `resourceId`, `iban`, `bookingDate`, `valueDate`, `transactionAmount { amount, currency }`, `creditorName`, `debtorName`, `remittanceInformationUnstructured`, `entryReference`. Своих синонимов для тех же понятий не придумывай.
- Суммы в API передаются строками (`"3247.50"`). Не превращай их во `float`: используй `Decimal` в Python, строку или целые тетри в TypeScript.
- Валюта — по ISO 4217 (`GEL`, `USD`, `EUR`). Суммы в разных валютах не складывай без явной конвертации по курсу.
- Даты — ISO 8601. `bookingDate` — это дата. Время храни со смещением, часовой пояс Asia/Tbilisi (`+04:00`).
- Каждый исходящий запрос получает новый `X-Request-ID` (UUID v4). Также передаются `Consent-ID`, `PSU-IP-Address` и `Authorization: Bearer <token>`.
- Токен живёт 1 час, его обновляют через `refresh_token`. Токены и `Consent-ID` в коде не зашиваются.
- Счета и транзакции работают с согласием v1, кредиты и сбережения требуют согласия v2.
- Песочница нарочно выдаёт сбои (`502 SERVICE_UNAVAILABLE`, «Injected synthetic failure») и задержки до 15 секунд. Поэтому у клиента:
  - таймаут на каждый запрос;
  - повтор с экспоненциальной задержкой и джиттером, максимум 3 попытки, только для идемпотентных GET и только при 5xx или таймауте;
  - `X-Request-ID` в логе на каждую попытку.
- Ошибки наш шлюз отдаёт в том же формате, что и песочница: `application/problem+json` с полями `type`, `title`, `status`, `code`, `detail`, `tppMessages[{ category, code, text }]`.

## 9. Тесты

- Каждый новый функционал покрыт тестами в том же изменении: функция, эндпоинт, правило, сценарий интервью, преобразование данных.
- Исправление бага начинается с теста, который воспроизводит баг и падает.
- Имя теста описывает поведение:
  - `test_pti_limit_uses_rules_version_in_force_on_application_date`;
  - `it('retries GET transactions after injected 502')`.
- Один тест проверяет одно поведение. Структура Arrange-Act-Assert, без логики и циклов внутри теста. Набор однотипных случаев — через `pytest.mark.parametrize` или `it.each`.
- Модульные тесты не ходят в сеть. HTTP мокается, ответы песочницы лежат в `test/fixtures/` или `tests/fixtures/`.
- Тесты детерминированы: фиксированные seed и время, никакой зависимости от порядка запуска.
- Проверяй и граничные случаи, а не только успешный путь: пустые данные, ошибки песочницы, истёкший токен, плохой кадр, несовпадение валют.
- Контроллеры NestJS покрываются e2e-тестами через supertest, сервисы — модульными тестами.
- Нельзя удалять, пропускать (`skip`) или ослаблять тест, чтобы он позеленел. Если тест неверен, исправь его и объясни причину в коммите.

## 10. Безопасность и данные

- Репозиторий публичный. В git не попадают ключи, токены, `.env`, материалы организаторов (`docs/hackathon/`), исследования (`docs/research/`) и реальные персональные данные. Текст исследований не копируй в файлы под git; ссылаться на первоисточники (Geostat, приказы NBG) можно. Переменные окружения описываются в `.env.example` без значений.
- Используем только синтетические данные. Имена и номера в примерах — выдуманные.
- Токены, ключи и биометрию не пишем в логи.
- Входные данные проверяются на границе: DTO в NestJS, pydantic в Python.
- Ответ LLM считается недоверенным вводом. Он всегда проверяется по строгой JSON-схеме, а при ошибке результат INCONCLUSIVE, а не «как получится».
- Новые зависимости — только известные и поддерживаемые, с точной версией. Подозрительное имя пакета обсуждается до установки.

## 11. Продуктовые ограничители

Это требования регулятора и жюри, их нельзя нарушать.

- Статус заявления (VERIFIED / PARTLY / NOT_VERIFIED / CONTRADICTED / INCONCLUSIVE) ставят только версионные правила из YAML, никогда не текст LLM.
- В данных, моделях и интерфейсе нет полей и признаков «честности», «лжи», эмоций, стресса и любых атрибутов, выведенных из лица или голоса.
- Автоматического отказа нет. Худший исход — передача кредитному специалисту или физический выезд.
- Интервьюер никогда не сообщает заёмщику вердикт.
- Плохое качество кадра или связи даёт INCONCLUSIVE, а не FAIL.
- Каждый кадр-доказательство хранится по SHA-256 и попадает в хэш-цепочку аудита. Журнал аудита только дописывается.
- Решение специалиста против рекомендации требует письменной причины.
- Значения правил NBG (PTI, LTV, пороги) живут только в конфиге с датой вступления в силу.
- Детей не снимаем и не обрабатываем.

## 12. Git

- Работаем в `local-dev`, в `main` попадаем только через pull request.
- Коммиты на английском в формате Conventional Commits: `feat(server): add AIS consent flow`, `fix(income-engine): ...`, `test: ...`, `refactor: ...`, `docs: ...`, `chore: ...`.
- Один коммит — одно логическое изменение. Файлы добавляются по имени, а не через `git add .`.
- Не коммитим сгенерированное: `income-engine/data/`, `models/`, `reports/`, `dist/`, `node_modules/`.
- Запрещено: `push --force`, прямой push в `main`, `--no-verify`, переписывание опубликованной истории.

## 13. Готово, когда

- [ ] Задача решена полностью, ничего лишнего не добавлено.
- [ ] Новый функционал покрыт тестами, все проверки компонента зелёные.
- [ ] Имена понятны без комментариев, комментарии только «почему».
- [ ] Нет мёртвого кода, отладочного вывода и зашитых секретов.
- [ ] Ограничители §11 не нарушены.
- [ ] README компонента обновлён, если изменились запуск, эндпоинты или переменные окружения.
