# Income Truth Engine

**Step 2 of [Virtual Field Visit](../README.md) · AI in Finance · Problem space 01: Credit Risk & Lending**

Lending to Georgians the credit bureau can't see. The engine reads a borrower's consented bank
transactions, estimates their **real income with an uncertainty band**, applies the **NBG PTI and LTV
limits**, scores 12-month default risk with a **transparent, explainable model**, proposes a compliant
offer (including a **harvest-shaped repayment schedule** for seasonal earners), and leaves the final
decision to a **loan officer**, with every decision written to a **tamper-evident audit log**.

> ⚠ **All data is synthetic.** No real person, account or bank is represented. See `docs/DATA_CARD.md`.

## Results (out-of-time test: 3,671 July 2026 applications, trained on July 2025)

| | Traditional process¹ | Income Truth Engine |
|---|---|---|
| Approval rate | 54.8% | **84.5%** |
| Expected bad rate² | 4.38% | **3.72%** |
| Expected loss rate | 2.92% | **2.08%** |
| Thin-file applicants approved | 0 | **1,155** |
| Income-fakers approved | 35 | **10** |
| Approvals breaching PTI on true income | 21.5% | **10.6%** |
| Median income error | 13.2% (declared) | **5.0%** |
| AUC, all / thin-file | 0.805 / 0.744 | **0.852 / 0.850** |
| Approval gap between regions / age groups | 26.7% / 32.0% | **6.8% / 2.5%**³ |

¹ Bureau score ≥ 600, thin files declined, amount capped at the NBG PTI limit on *declared* income.
² Each approved offer's true default probability (known because the data is synthetic).
³ Engine run at the traditional process's bad rate, where it approves 90.5% of applicants.

More: harvest-shaped schedules cut seasonal borrowers' default risk by 20%;
the engine reaches 90% of the best possible Gini on this data; NBG's 2027 PTI thresholds would lower the
maximum loan for 25% of applicants and compliant credit by 16%;
150 ms per application, 2,007 applications/second in batch on one CPU.

Full results page: `reports/results.html` · charts for slides: `reports/figures/` · all numbers: `reports/metrics.json`.
These files, `data/` and `models/` are generated by `make all` and are not committed.

## Part of the platform

This engine is also installed into the collateral engine's environment (`pyproject.toml` makes the
package `ite` installable), where the platform API and console call it in process and combine its
PTI-compliant amount with the collateral's LTV in one full application; see
[`../collateral-engine/README.md`](../collateral-engine/README.md). There is no automatic refusal:
an application the engine cannot offer is referred to the loan officer (`REFER`); only the officer
may decide to reject, with a written reason.

## Run it on its own

```bash
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
make all          # generate data → train → evaluate → build report → run 30 tests (~2 min)
make app          # loan-officer & supervisor app on http://localhost:8501
make api          # REST API on http://localhost:8000/docs  (header X-API-Key: demo-key-change-me)
# or on its own in Docker: docker build -t income-engine . && docker run -p 8000:8000 income-engine
```

Without `make`: `PYTHONPATH=src python -m ite.synth`, then `python -m ite.train`, `python -m ite.report`,
`python -m pytest -q`, `streamlit run app/streamlit_app.py`.

## Architecture

```
consented transactions ─▶ categoriser (Georgian/Latin text, char n-grams)
                         ─▶ circular-transfer detector
                         ─▶ features (income by month, seasonality, savings, bills, betting…)
                         ─▶ income model: quantile LightGBM, conformal-calibrated P10/P25/P50/P90
application ───────────▶ NBG rules engine (versioned YAML, dated) ─▶ max compliant amount
                         ─▶ risk model: champion–challenger (scorecard vs monotone GBM)
                         ─▶ reasons (exact contributions / SHAP) in Georgian + English
                         ─▶ offer, path to yes, harvest-shaped schedule, GEL −20% stress
                         ─▶ officer decides (override needs a reason) ─▶ hash-chained audit log
```

| Path | What |
|---|---|
| `src/ite/synth.py` | Synthetic data generator (hidden ground truth, cohorts, fraud, cash income) |
| `src/ite/categorise.py` | Transaction categoriser |
| `src/ite/features.py` | Borrower features, circular-transfer detection |
| `src/ite/models.py` | Income quantile model, champion–challenger risk model, baseline |
| `src/ite/rules.py` + `config/nbg_rules.yaml` | NBG PTI/LTV rules, versioned by date |
| `src/ite/schedule.py` | Annuity and harvest-shaped schedules (equal present value) |
| `src/ite/explain.py` | Reasons and borrower letter (template-filled, no free-form AI text) |
| `src/ite/audit.py` | Tamper-evident audit log |
| `src/ite/engine.py` | Single decision path for API, app and batch |
| `src/ite/train.py`, `report.py` | Training, out-of-time evaluation, report, cards |
| `api/main.py` | FastAPI service (`/v1/assess`, `/v1/decisions`, `/v1/audit/verify`, `/health`) |
| `app/streamlit_app.py` | Loan review, portfolio results, PTI 2027 simulator, cards |
| `tests/` | 28 tests: NBG rules, schedules, audit tampering, leakage, API, release gates |

## Guardrails

- Offers can never exceed the NBG PTI/LTV limit; the rules version in force on the application date is applied.
- Champion–challenger: the simpler model is kept unless the complex one gains > 0.005 AUC (it did not).
- Business-logic sign checks; counter-intuitive features are dropped automatically and logged.
- Gender, age and region are not model inputs; used only for fairness monitoring.
- Human approval for every decision; overrides need a written reason; hash-chained audit log.
- Wide income bands, circular transfers and borderline risk go to the review queue.
- Drift (PSI), calibration and a lari −20% stress test are reported on every training run.
- Release gates in `tests/test_engine.py` fail the build if accuracy, calibration or sign checks regress.

## Limitations

Synthetic data only; real performance is unknown until a pilot in NBG's AI sandbox. Production income
training needs verified income labels. Reject inference is needed on real lending data. NBG must confirm
how PTI applies to non-equal schedules. Verify every rule value in `config/nbg_rules.yaml` with NBG.
Details: `docs/MODEL_CARD.md`, `docs/DEPLOYMENT.md`.
